# 整合式影像處理軟體

以高解析度灰階影像為主的 Windows 桌面影像處理與檢測工具。技術採用 C# WinForms、.NET Framework 4.7.2 與 OpenCvSharp。

## 專案狀態

- 文件快照：2026-10-07。
- 最新已推送提交：`0a4c7a5 Run result review defect analyses concurrently`（`main`，目前與 `origin/main` 同步）。
- 最新已推送的紋理異常仍是實驗性算法。使用者實測回報：正常底材紋理也會誤報，目標痕跡在熱圖上沒有明顯反應；尚不能用於正式良／不良判定。
- 紋理診斷熱圖已在 `86d5a69` 納入版本，提供最終分數、局部暗像素密度與方向候選分數檢視；它只協助分析，不改變檢測判定。
- 工作目錄在本次文件編輯前乾淨。最近一次 Debug 建置成功；結果確認中的多類缺陷分析已支援依參數勾選平行執行，但尚未完成真實產線影像端到端驗收。
- 頻域區域能量與結果整合已在程式中；尚未用實際影像完整驗收異常框及整體 NG 判定。大圖平移／清晰度也仍待使用者以實際圖片確認。

## 主要流程

```text
原圖
  -> 前處理
  -> 影像處理（Edge / Threshold）
  -> 影像關聯
  -> 整合區塊與區塊處理
  -> 物件定義（連通元件、篩選、編號、可選旋轉資訊）
  -> 檢測參數（平場、尺寸量測、良品條件、缺陷四核心、頻域異常、紋理異常）
```

檢測參數包含尺寸量測與尺寸良品條件、平場校正、四個缺陷檢測核心、頻域區域能量及紋理異常分析。各缺陷核心有獨立設定與預覽；單核心「套用」只更新該核心，「執行四核心檢測」才執行全部核心。頻域頁以平場校正灰階影像及可選對比倍率分析區域能量；紋理異常則比較檢測範圍內各方向路徑的暗像素密度與兩側背景。舊版自動方向線分析已移除。影像 MASK 來源、檢測範圍及結果保存方式詳見專案交接文件。

「參數結果確認」是唯讀檢測流程：選擇已保存的檢測參數、載入相同影像尺寸的圖片，再按「執行確認」。左側可切換量測位置、平場校正、缺陷平場／條件一至三、頻域異常、紋理異常與整合結果；右側檢視量測統計、尺寸良品條件和缺陷判定。尺寸條件先判 A 規，A 不符合才判 B 規，B 規可獨立使用。此頁不提供參數編輯；實際圖片結果仍待驗收。

目前規劃的使用流程是工程師先設定檢測參數，使用者再選擇參數與圖片、明確執行檢測並查看影像和判定；設定與檢視分開的方向合理。尚未完成的檢測設定防呆、判定政策確認及實圖驗收，是後續完善項目，不代表流程規劃需要重做。

## 架構評估

- **流程方向合理**：設定、執行與唯讀結果檢視的職責有區分，物件 ROI、平場、尺寸量測、缺陷核心與結果整合的處理順序清楚。
- **程式仍屬單體 WinForms 的逐步拆分階段**：`partial MainForm` 讓功能比較容易定位，但各檔案仍共享主視窗狀態；拆檔尚不等於模組可獨立測試或執行。
- **結果確認尚未完全隔離執行狀態**：結果確認頁會設定目前作用中的參數，並沿用主視窗的圖片、物件定義與平場校正流程。雖然操作頁是唯讀的，內部仍可能受共用狀態影響，尚未成為獨立的檢測工作階段。
- **平行運算需以實圖確認資源上限**：結果確認的平行模式會同時啟動一般缺陷核心，以及已納入且尚無有效快取的頻域／紋理分析；各流程內部也可能依物件 ROI 平行。這代表併發工作增加，不是固定建立「ROI 數 × 核心數」個執行緒；仍需測量 CPU／記憶體壓力及取消行為。
- **參數持久化可維護性是風險**：設定模型為強型別，但 INI 讀寫採手動欄位序列化；目前沒有明確的格式版本／遷移機制，舊參數相容性需持續驗證。
- **驗證基礎仍需補強**：目前未找到專用自動化測試專案；建置成功不能替代影像算法、參數往返與 GUI 端到端驗收。

建議優先建立「檢測工作階段輸入快照／結果快照」，使結果確認不再借用主流程的可變狀態；再為尺寸計算、缺陷分割與合併、參數讀回建立測試。之後逐步抽離純運算服務、設定平行度上限與影像記憶體用量，避免只為降低檔案行數而進行大規模重寫。詳細風險與建議順序見 [PROJECT_HANDOFF.md](PROJECT_HANDOFF.md)。

## 最近顯示效能調整

- 大圖平移時，依可視區域大小限制快取磚塊繪製數；上限目前為 64 塊，超過時以預覽圖保持拖曳流暢，放開後再載入細節。
- 預覽長邊上限提高至 3072，改善中低倍率預覽被放大時的模糊。
- 待量測畫面的平行線疊圖會依縮放抽樣顯示；量測計算仍使用完整線數。獨立線段繪圖也已避免路徑意外相連。
- 使用者回報 `0.03X` 拖曳順、`0.04–0.06X` 曾卡頓，`0.14X` 曾模糊。64 塊上限與 3072 預覽是最新折衷，尚待使用者用同一張大圖確認流暢度、清晰度與 MASK 對位。

## 頻域分析近況

- 頻域預覽與掃描共用同一份 8-bit 灰階影像；「啟用對比調整」勾選時，在平場校正影像上套用對比倍率，取消時使用倍率 1.0。舊參數缺少此欄位時預設啟用，維持原本行為。
- 目前僅執行重疊視窗的區域能量分析，並顯示能量熱圖及異常框。原本將完整 DFT 頻譜功率加總，現以 Parseval 等價的 MASK 內加窗平方平均計算；保留視窗尺寸、半格步距與結果統計定義，不再為全頻譜總和執行 DFT。
- 每個掃描視窗直接走灰階影像、MASK 與 Hanning 矩陣的列指標，兩趟完成 MASK 平均與加窗能量；不為每格配置子 Mat 或呼叫多次 OpenCV 矩陣運算。計算區塊使用受控 unsafe 記憶體存取，專案已啟用 `AllowUnsafeBlocks`。
- 分析狀態會分列平場來源準備、掃描牆鐘、掃描格數，以及 ROI 格迴圈／預覽的累計時間；平行處理時累計時間可能大於實際等待時間。真正畫面重繪時間不包含在分析總耗時內。
- 自動方向線分析及其敏感度／熱圖／異常框設定已從介面、運算和參數保存移除；舊 INI 內相關未知欄位會被忽略，重新保存時不再寫出。
- 「結果整合」可選擇納入頻域異常；只把有效結果中的異常掃描格作為中性候選，與暗／亮缺陷依 ROI 和合併距離分組，且不繞過既有暗／亮／亮暗合併限制。來源會列為「頻域異常」，頻域單獨群組用青色框。
- 「結果整合」亦可選擇納入紋理異常，將通過暗紋密度分析的片段作為候選；整合位置和真實影像判定仍待實圖驗收。
- 結果確認中若選擇納入且頻域啟用，會重用有效頻域快取，沒有有效結果才自動分析；頻域分析失敗或過期會將整合判定設為待確認。整合群數會影響缺陷 NG 判定。

## 結果確認平行運算

- 平行選項啟用時，結果確認會以 `Task.WhenAll` 同時執行一般缺陷條件，以及已設定納入整合、啟用且沒有有效快取的頻域異常與紋理異常；已有效的分析結果會重用，不重複計算。
- 平行缺陷總耗時使用共同工作的牆鐘時間，不把各任務耗時相加；各演算法內部仍可能按物件 ROI 平行，因此實際效能取決於 ROI 數、影像大小、快取與硬體。
- 此次改動已 Debug 建置，但仍應用代表性大圖驗證結果一致性、記憶體用量、取消與例外收尾。平行勾選關閉時維持依序執行。

## 多檢測參數插入規劃

- 已確認的需求是一次選取兩個獨立參數檔匯入，使兩組設定同時保留；之後每次選一組載入／執行，不要求兩組同時運算。
- 目前尚未實作。現有「檢測參數讀取」匯入只接受一組參數，並以該檔完整取代目前設定；直接把第二組參數物件附加到清單，可能因 ROI、MASK、物件定義等相依資料及內部 ID 共用而互相干擾。
- 實作前需定義整組參數與相依資料的匯入邊界、ID 重映射、重名處理、兩檔原子式驗證／匯入，以及檢測執行中禁止切換的規則。詳細評估與建議見 [PROJECT_HANDOFF.md](PROJECT_HANDOFF.md)。

## 紋理異常近況

- 新版不再以單格特徵偏離或逐格線段偵測為主；先對平場校正灰階影像做局部高斯基準，再統計每個紋理格中比周圍暗至少 4 灰階級的像素占比，讓「暗色紋理區塊比較密集」能形成可累積訊號。
- 在檢測範圍內以 0.5 度步距掃描方向投影，將中心路徑的暗像素密度與兩側背景比較；兩側需有足夠有效支撐，避免檢測範圍邊界造成假峰值。局部支撐通過後才標示格子，並合併短間斷、依最小面積形成異常區域。
- 使用者提供的示意圖以離線原型測試時，目標斜線在 4、8、16 px 格大小皆成為最強候選。這不是應用程式對真實產線影像的驗收，也不能證明實際誤判率；高紋理背景仍需拿真實良品／不良品影像調參驗證。
- 使用者在公司影像上的實測顯示，誤報外觀像正常底材紋路，且欲檢痕跡旁沒有熱圖突出；即使提高敏感度也仍會誤報並漏檢。因此目前方法沒有足夠的正常紋理模型，單純調嚴參數不是合適的解法。
- 紋理診斷熱圖來源選單提供「最終檢出分數」、「局部暗像素密度」與「方向候選分數」。切換來源後需重新執行分析；診斷圖依物件分別拉伸色階，僅影響顯示，不參與判定，也不會上傳影像。超大區域的診斷圖可能為了顯示而降採樣。
- 診斷判讀：局部暗像素密度看不到目標，表示目前的暗紋特徵沒有表達目標；密度有反應但方向分數沒有，問題較可能在方向累積／背景帶比較；方向分數有反應但最終結果沒有，才往門檻、形態學連接或區域篩選追查。可用同一物件的正常區與目標區對照。
- 真實公司影像不需傳出設備；目前診斷版本尚未完成 GUI 和實圖驗收。新的檢測算法應先以本機良品與不良品確認「目標和正常底材的分數分布」，再決定是否採用相對正常紋理的參考模型或其他特徵，不宜繼續盲目增加敏感度參數。
- 目前敏感度沿用既有設定，較高代表較嚴格；像素暗度門檻目前固定為局部基準差 3（OpenCV Binary threshold 會留下高於 3 的暗差像素）。計算範圍使用物件檢測區域多邊形，不代表已串接每一個前處理核心的來源 MASK。
- 全方向累積每個物件約需處理 360 組方向投影，成本隨有效紋理格數增加；尚未做大型 ROI 的實際耗時基準。若使用者影像處理時間過長，應先量測方向掃描和局部驗證耗時，再調整角度步距或採粗掃後細化。

## 建置

以 Visual Studio 開啟根目錄的 `MyApp4.sln`，還原 NuGet 套件後選擇 `Debug` / `Any CPU` 建置。也可使用：

```powershell
msbuild .\MyApp4.sln /t:Build /p:Configuration=Debug /p:Platform="Any CPU"
```

主專案為 `IntegratedImageProcessingApp\IntegratedImageProcessingApp.csproj`。此舊式 .NET Framework 專案使用明確的 `<Compile Include=...>` 清單；新增 C# 檔案時要一併更新專案檔。

## 程式結構

- `IntegratedImageProcessingApp\Controls`：影像顯示、縮放平移、大型影像來源與預覽／分塊繪製。
- `IntegratedImageProcessingApp\Forms`：WinForms 主視窗與各功能流程；`MainForm` 以 partial 檔分工，仍負責主要 UI 協調。
- `IntegratedImageProcessingApp\Services`：OpenCV 運算、INI 參數、灰階解碼及 ROI／MASK 快取與建置。

完整檔案職責、功能進度、資料保存語意、建置狀態、已知限制與接手驗收步驟請見 [PROJECT_HANDOFF.md](PROJECT_HANDOFF.md)。
